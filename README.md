
# 🛡️ Real-Time Security Operations Center (SOC) Dashboard

> An end-to-end SOC platform integrating Wazuh, OpenSearch, Node.js, TypeScript, React, and Socket.IO for security-event ingestion, normalization, correlation, incident management, and real-time visualization.

## 📌 Overview

This project is a security monitoring platform designed to demonstrate how telemetry generated by monitored endpoints can move through a centralized detection pipeline and become actionable incidents for a security analyst.

The architecture connects **Wazuh** for endpoint monitoring and detection, **Wazuh Indexer/OpenSearch** for alert storage and search, a custom **Node.js/TypeScript backend** for continuous ingestion and event correlation, and a **React dashboard** for analyst visualization.

### Core pipeline

```text
Kali / Monitored Endpoint
          ↓
     Wazuh Agent
          ↓
    Wazuh Manager
          ↓
 Wazuh Indexer / OpenSearch
          ↓
 Continuous Backend Polling
          ↓
      Deduplication
          ↓
   NormalizationService
          ↓
    CorrelationEngine
          ↓
   Incident / Risk State
          ↓
       Socket.IO
          ↓
    React SOC Dashboard
          ↓
   Security Analyst
```

The main goal is to transform raw security telemetry into correlated incidents while maintaining a real-time connection between the security infrastructure and the analyst dashboard.

---

# 🎯 Objectives

- Collect real security telemetry from monitored systems.
- Integrate directly with Wazuh and its OpenSearch-based Indexer.
- Continuously retrieve newly indexed alerts.
- Track the latest successfully processed event.
- Deduplicate alerts using the Indexer document `_id`.
- Normalize raw Wazuh events into a consistent structure.
- Correlate related security events.
- Generate structured incidents.
- Calculate and display incident risk/severity.
- Maintain backend incident state.
- Push updates to the React frontend through Socket.IO.
- Update the dashboard without requiring manual browser refreshes.
- Provide a controlled cybersecurity laboratory for demonstrations.
- Provide an extensible foundation for future AI-assisted analysis and attack visualization.

# ⚡ Core Features

## 1. Real-Time Wazuh Integration

The backend communicates with the Wazuh Indexer/OpenSearch API and continuously searches for security events.

The intended production path is based on **real Wazuh data**, not mock incidents or manually seeded dashboard metrics.

---

## 2. Continuous Polling

The ingestion worker periodically queries the Indexer for alerts newer than the current high-water mark.

```text
Poll
 │
 ├── Query Indexer
 │
 ├── Retrieve candidate alerts
 │
 ├── Deduplicate by _id
 │
 ├── Process genuinely new alerts
 │
 └── Advance watermark
 │
 ▼
Next Poll
```

A polling lock can be used to prevent overlapping requests when the Indexer takes longer than expected to respond.

---

## 3. High-Water Mark

The backend maintains a timestamp representing the latest successfully processed alert.

```text
Previous watermark
        │
        ▼
──────────────────────────────────────────► Time
        │
        │ Query for newer events
        ▼
                     New alert
                        │
                        ▼
                  Process event
                        │
                        ▼
                 Advance watermark
```

This prevents old events from repeatedly being treated as new events.

---

## 4. Deduplication

Every OpenSearch document has an `_id`. The ingestion layer can maintain a set of processed IDs.

Example:

```text
Poll #1

Alert A → NEW
Alert B → NEW
Alert C → NEW

Poll #2

Alert A → DUPLICATE
Alert B → DUPLICATE
Alert C → DUPLICATE
Alert D → NEW
```

Only genuinely new events should proceed through the normalization and correlation pipeline.

---

# 🔄 Delayed-Indexing Protection

Security events may take a short amount of time to travel through:

```text
Endpoint
   ↓
Wazuh Agent
   ↓
Wazuh Manager
   ↓
Indexer
   ↓
Searchable document
```

A small overlap window can therefore be used when querying the Indexer.

```text
Previous watermark
        │
        ▼
───────┬────────────────────────────────────► Time
       │
       │◄── overlap ──►
       │
       └──── Query window ────────────────►
```

The overlap allows delayed events to be discovered while `_id` deduplication prevents duplicate processing.

---

# 🧠 Alert Normalization

Raw Wazuh documents contain different fields depending on the event type.

The normalization layer converts these documents into a consistent internal representation.

Typical normalized information can include:

- Event ID
- Timestamp
- Source IP
- Target IP
- Username
- Hostname
- Rule ID
- Rule description
- Severity
- Event category
- MITRE information when present
- Original event data

Conceptually:

```text
Raw Wazuh Alert
       ↓
NormalizationService
       ↓
NormalizedAlert
       ├── timestamp
       ├── source
       ├── target
       ├── severity
       ├── description
       ├── agent
       ├── rule
       └── techniques
```

The system should use information actually present in the source alert rather than inventing security attributes.

---

# 🔗 Event Correlation

A real security incident can consist of multiple related alerts.

For example:

```text
Authentication Failure
        +
Invalid Username
        +
Repeated Activity
        +
Same Target
        ↓
Correlated Activity
        ↓
Security Incident
```

The correlation engine groups events according to configured relationships such as target, agent, and time window.

This provides a higher-level view of activity for analysts.

# 🤖 AI Analyst (OpenRouter) — setup

The AI Analyst is a ChatGPT-style assistant at `/ai-analyst`. All AI calls go **through the backend**; the browser never sees the API key or any Wazuh credential.

```text
Alert Queue / Investigation ──► POST /api/ai/chat
                                   │ 1. rate-limit (local)          6. OpenRouter (key stays here)
                                   │ 2. collect evidence from Wazuh ──► 7. un-mask reply
                                   │ 3. restrict to agent 001 (win-11)
                                   │ 4. cap + collapse alerts (never "every raw alert")
                                   └ 5. mask IPs, users, hosts, secrets
```

**Environment variables** (copy `backend/.env.example` to `backend/.env`; never commit `.env`):

| Variable | Purpose | Default |
|---|---|---|
| `OPENROUTER_API_KEY` | **Required for AI.** Without it the dashboard works and the AI page shows "configuration required". | – |
| `OPENROUTER_MODEL` | Open-weight model id. Free models change; pick one from openrouter.ai/models. | `meta-llama/llama-3.3-70b-instruct:free` (unverified) |
| `OPENROUTER_FALLBACK_MODELS` | Comma list tried on 404 / 429 / 5xx | – |
| `AI_TIMEOUT_MS`, `AI_MAX_TOKENS`, `AI_TEMPERATURE` | Request limits | 60000 / 1800 / 0.2 |
| `AI_MAX_EVIDENCE_ALERTS`, `AI_EVIDENCE_WINDOW_HOURS` | Evidence size / window | 40 / 24 |
| `AI_RATE_LIMIT_PER_MINUTE` | Local limiter protecting free quota | 10 |
| `AI_ENABLED` | Kill switch | true |
| Live investigation scope | Fixed in backend code; environment overrides are intentionally unsupported. Only Wazuh agent **001** (`win-11`) can be investigated. | Immutable |

**New endpoints (additive):** `GET /api/ai/status`, `POST /api/ai/chat`, `POST /api/ai/preview` (shows the masked evidence that would be sent), `GET /api/alerts/summary`, `GET /api/alerts/:id`. Existing routes are unchanged.

**Tests:** `cd backend && npm test && npm run typecheck`; `cd frontend && npm run build`. Optional browser tests: see `e2e/`.

**Run:** `cd backend && npm run dev` and `cd frontend && npm run dev`.
